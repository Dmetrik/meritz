# 표준 Product Spec 양식

빈 뼈대는 `assets/SPEC_TEMPLATE.md`에 있다. 이 문서는 각 섹션에 **무엇을 쓰고 무엇을 쓰지
않는가**를 정의한다.

## 이 문서를 누가 읽는가

**기획자와 디자이너가 주 독자다.** 개발자도 보지만, 개발자는 아쉬우면 코드를 열어 볼 수 있고
기획자·디자이너는 그럴 수 없다. 그래서 양식이 두 부분으로 나뉜다.

| | 읽는 사람 | 담는 것 |
|---|---|---|
| **1부 제품** (필수 10) | 기획·디자인·개발 모두 | 왜 만드나, 누가 쓰나, 어떻게 쓰나, 화면, 기능, 안 하는 것 |
| **2부 개발 참고** (선택 6) | 개발자 | 데이터·API, 권한, 연동, 운영, 기술 제약 |

**1부에는 구현 용어를 쓰지 않는다.** 엔드포인트 경로, 함수 이름, 파일 경로, 라이브러리 이름이
1부에 나오면 잘못 쓴 것이다. 그런 건 전부 2부로 간다.

## 파일 이름과 위치

```
<docsDir>/<specIdPrefix>-<3자리 번호>-<영문 슬러그>.md
예) docs/specs/DM-001-payment-widget.md
```

번호는 `docsDir`의 기존 파일 중 가장 큰 값 + 1. 슬러그는 소문자·하이픈만 쓴다. 파일 이름은
한 번 정하면 바꾸지 않는다 — 위키 페이지와 이슈에서 이 경로를 참조하기 때문이다.

## frontmatter

```yaml
---
spec_id: DM-001              # 파일명과 동일한 ID. 고유값
title: 결제 위젯             # 제품/기능 이름 (config.language 기준)
owner: 김태인 / PO팀          # 문서 책임자. 모르면 "미지정"
status: draft                # draft | active | deprecated
spec_version: 1.0.0          # 문서 버전 (제품 버전 아님)
last_synced_commit: a1b2c3d  # 이 문서가 반영한 마지막 커밋 (짧은 해시)
last_synced_at: 2026-09-05   # YYYY-MM-DD
repo: acme/payment-widget    # 대상 리포. 모노레포면 패키지 경로까지
tracker_ref: DM-142          # 대표 이슈 키. 없으면 생략
wiki_url:                    # 발행 후 자동 기록. 처음엔 비워 둔다
---
```

`last_synced_commit`이 이 양식의 핵심이다. 갱신은 전적으로 이 값을 기준점으로 동작한다.

### `spec_version` 올리는 기준

| 변경 | 올림 |
|---|---|
| 기능 삭제, 대상 사용자 자체가 바뀜, 안 하기로 했던 걸 하게 됨 | major (1.2.0 → 2.0.0) |
| 기능·화면 추가 | minor (1.2.0 → 1.3.0) |
| 문구 수정, 오타, 근거 보강 | patch (1.2.0 → 1.2.1) |

## 섹션 마커

부분 갱신을 가능하게 하는 장치다. **마커를 지우거나 형태를 바꾸면 갱신이 동작하지 않는다.**

```markdown
<!-- spec:section id=features -->
## 5. 무엇을 할 수 있나

(코드에서 추출한 내용. 갱신할 때마다 이 영역은 통째로 다시 쓰인다)

<!-- spec:human -->
> 결제 실패 재시도 3회는 PG사 정책상 상한이라 못 늘림. — 2026-08 PO팀
<!-- /spec:human -->
<!-- /spec:section -->
```

- `spec:section` — 갱신 단위. `id`는 아래 정의된 값만 쓴다
- `spec:human` — **사람 영역.** 갱신 시 바이트 단위로 그대로 옮긴다. 섹션 어디에나 여러 개
  둘 수 있다. 다듬기·요약·위치 이동 모두 금지
- `> ❓ 확인 필요: <질문>` — 코드로 확답할 수 없어 사람 답이 필요한 지점

## 1부 — 제품 (필수 10)

| id | 제목 | 채우는 주체 | 내용 |
|---|---|---|---|
| `summary` | 한 줄 요약 | 자동+사람 | 누구의 어떤 불편을 어떻게 더는지 3줄 이내 + 상태·담당·최종 갱신 표 |
| `problem` | 1. 왜 만드나 | **사람** | 코드에 답이 없다. `spec:human`으로 비워 두고 질문을 남긴다 |
| `users` | 2. 누가 쓰나 | **사람** | 주 사용자와 사용 맥락. 코드에서 역할 구분이 보이면 그것만 사실로 적고 나머지는 질문 |
| `flows` | 3. 어떻게 쓰나 | 자동+사람 | **디자이너가 제일 먼저 보는 곳.** 대표 흐름 1~3개를 사용자 행동과 화면 결과로. 각 흐름에 "잘 안 될 때"를 붙인다 |
| `screens` | 4. 화면 | 자동+사람 | 화면별로 무엇을 하는 곳인지·누가 들어오는지·거기서 할 수 있는 것. 빈 상태와 오류 상태를 반드시 적는다 |
| `features` | 5. 무엇을 할 수 있나 | 자동 | 기능 한 줄씩. **사용자가 얻는 결과**로 쓴다. "쓰는 사람" 열로 역할을 표시 |
| `scope` | 6. 안 하는 것 | 자동+사람 | 이유와 함께. 여기가 비면 나중에 반드시 분쟁이 난다 |
| `metrics` | 7. 무엇이 좋아지면 성공인가 | **사람** | 코드에 답이 없다 |
| `open-questions` | 8. 확인이 필요한 것 | 자동 | 문서 전체의 `❓ 확인 필요`를 모은 체크리스트. **갱신마다 다시 만든다** |
| `changelog` | 9. 변경 이력 | 자동 | 최신이 위. 코드가 아니라 사용자에게 무엇이 달라졌는지 |

### `flows`를 잘 쓰는 법

라우팅과 핸들러를 따라가면 흐름은 재구성할 수 있다. 다만 **코드 순서가 아니라 사용자 순서로**
쓴다.

```markdown
### 흐름 1 — 음료 주문하기

1. 오늘의 메뉴에서 마실 것을 고른다. 품절된 메뉴는 목록에 나오지 않는다
2. 사이즈를 고르고 요청사항을 100자까지 적을 수 있다
3. 주문하면 "준비중"으로 접수되고, 바리스타 채널에 주문 번호가 올라간다

**잘 안 될 때** — 사이즈를 안 고르거나 요청사항이 100자를 넘으면 접수되지 않는다.
로그인 정보가 없으면 주문 자체가 실패한다.
```

### `open-questions`는 자동으로 만든다

문서 안의 모든 `❓ 확인 필요`를 훑어 체크리스트 표로 모은다. 원래 자리의 `❓`는 그대로 두고,
이 섹션은 **색인** 역할만 한다. 갱신할 때마다 전체를 다시 만든다.

```markdown
| | 섹션 | 확인할 내용 | 답해줄 사람 |
|---|---|---|---|
| ☐ | 1. 왜 만드나 | 어떤 불편에서 출발했나 | |
| ☐ | 7. 성공 지표 | 어떤 숫자가 얼마나 달라져야 하나 | |
```

기획자가 문서를 열었을 때 **자기가 할 일이 한눈에 보이는 곳**이다. 여기가 이 문서의 실질적인
작업 목록이다.

## 2부 — 개발 참고 (선택 6)

`config.sections.optional`에서 켜고 끈다. 기본은 전부 켜져 있고, 근거가 없으면 섹션째 생략한다.
**여기서는 구현 용어와 `경로:줄번호` 인용을 자유롭게 쓴다.**

| id | 제목 | 내용 |
|---|---|---|
| `data-api` | A. 데이터와 API | 다루는 데이터 표 + 엔드포인트 표(메서드·경로·용도·인증·정의 위치) |
| `permissions` | B. 권한과 보안 | 역할별 접근 범위, 인증 방식, 민감정보 취급. **토큰·키 값은 절대 옮겨 적지 않는다** |
| `dependencies` | C. 연동과 의존성 | 외부 서비스(없으면 어떻게 되는지 포함), 환경변수 **이름만**, 주요 라이브러리 |
| `ops` | D. 배포와 운영 | 배포 방식, 실행 환경, 롤백, 모니터링 |
| `tech-notes` | E. 기술적 제약과 알려진 이슈 | 구현상의 문제. **사용자에게 영향이 가는 것은 여기 두지 말고 1부에 사람 말로 적는다** |
| `sources` | F. 근거 | 섹션별로 어떤 파일을 봤는지. 본문 서술의 출처를 확인하는 곳 |

## 문장 규칙

### 1부 — 사용자의 말로

- **구현 용어 금지.** 함수·파일·엔드포인트·라이브러리 이름이 1부에 나오면 잘못 쓴 것이다
- **`경로:줄번호` 인용을 본문에 달지 않는다.** 근거는 `sources` 섹션에 섹션 단위로 모은다.
  읽는 흐름을 끊지 않으면서도 출처를 확인할 수 있다
- 확인된 사실은 단정형으로. "품절된 메뉴는 목록에 나오지 않는다"
- 추론은 쓰지 않는다. `> ❓ 확인 필요:`로 남긴다
- 한 항목이 두 줄을 넘으면 쪼갠다

### 2부 — 정확하게

- `경로:줄번호`까지 적는다. `src/api/payments.ts:42`
- 표를 쓸 수 있으면 표를 쓴다
- 환경변수는 이름만. 값은 절대 넣지 않는다

## 기술 사실을 사람 말로 옮기기

코드에서 발견한 것을 1부에 적을 때는 **사용자가 겪는 일**로 바꾼다. 그대로 옮기면 기획자가
읽을 수 없고, 버리면 중요한 제약이 사라진다. 번역해서 양쪽에 적는다.

| 코드에서 본 것 | 1부에 적는 말 | 2부에도 남길 것 |
|---|---|---|
| `notifySlack`이 `async`인데 `await`가 없다 | "알림 전송이 실패해도 화면에는 정상으로 보인다" (흐름의 "잘 안 될 때") | 원문 그대로 + 근거 |
| 취소 엔드포인트가 없다 | "주문을 되돌릴 수 없다. 바리스타에게 직접 말해야 한다" (안 하는 것) | — |
| `SELECT *`로 전체 컬럼 반환 | (사용자 영향 없음 — 1부에 적지 않는다) | 원문 그대로 |
| `role === "staff"` 검사 | "바리스타만 들어올 수 있다" (화면의 "누가 들어오나") | 역할 표 + 근거 |
| DB에 상태 제약이 없다 | (사용자 영향 없음 — 1부에 적지 않는다) | 원문 그대로 |

판단 기준은 하나다. **사용자가 그 일을 겪는가?** 겪으면 1부에 사람 말로, 안 겪으면 2부에만.
