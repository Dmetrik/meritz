# Product Spec

바이브 코딩으로 제품이 빠르게 늘어나면 각자 다른 양식의 문서가 흩어지고, 만든 다음엔 아무도
갱신하지 않는다. 이 스킬은 그 두 가지를 해결한다. **코드에서 사실을 뽑아 표준 양식으로 쓰고,
코드가 바뀌면 바뀐 섹션만 다시 쓴다. 사람이 쓴 문장은 절대 건드리지 않는다.**

## 이 문서를 누가 읽는가

**기획자와 디자이너가 주 독자다.** 개발자도 보지만, 개발자는 아쉬우면 코드를 열 수 있고
기획자·디자이너는 그럴 수 없다. 이 전제가 문서의 모든 것을 결정한다.

양식은 두 부분이다. **1부 제품**(필수 10개 섹션)은 셋 다 읽고, **2부 개발 참고**(선택 6개)는
개발자가 읽는다. 1부에 엔드포인트 경로·함수 이름·파일 경로가 나오면 잘못 쓴 것이다.
코드에서 발견한 기술적 사실은 **사용자가 겪는 일로 번역해서** 1부에 적고, 원문은 2부에 남긴다.
번역하는 법은 `references/spec-format.md`의 마지막 절에 표로 있다.

## 언제 무엇을 하는가

| 상황 | 할 일 | 참고 문서 |
|---|---|---|
| 설정 파일이 없다 | 온보딩부터 (§1) | `references/onboarding.md` |
| 스펙 문서가 없는 제품이다 | 신규 작성 (§2) | `references/spec-format.md` |
| 스펙은 있는데 코드가 변했다 | 갱신 (§3) | `references/update-protocol.md` |
| 코드↔문서가 맞는지 알고 싶다 | 드리프트 점검 (§4) | `references/update-protocol.md` |
| 완성된 문서를 팀에 공유한다 | 발행 (§5) | `references/tools/<위키 타입>.md` |

**어떤 작업이든 시작 전에 반드시 `references/evidence.md`를 읽는다.** 자동 생성 문서가
버려지는 유일한 이유는 그럴듯한 거짓말이 섞여서다. 근거 규칙이 이 스킬의 핵심이다.

## 0. 설정 로드 (모든 작업의 첫 단계)

제품 리포 루트의 `.claude/product-spec.json`을 읽는다.

- **없으면** → §1 온보딩으로 간다. 임의로 만들어 진행하지 않는다.
- **있으면** → `docsDir`, `specIdPrefix`, `language`, `integrations` 세 슬롯을 기억한다.

`integrations`는 세 슬롯뿐이다. 회사마다 쓰는 툴이 달라도 이 구조는 같다.

| 슬롯 | 역할 | `type` 후보 |
|---|---|---|
| `tracker` | 이슈·티켓에서 "왜 만들었는가"를 가져온다 | `jira` `youtrack` `linear` `github` `none` |
| `chat` | 논의 스레드에서 결정 배경을 가져오고, 완성 문서를 알린다 | `slack` `none` |
| `wiki` | 완성 문서를 비개발 직군이 보는 곳에 발행한다 | `confluence` `notion` `none` |

각 슬롯의 `type` 값에 해당하는 `references/tools/<type>.md` **하나만** 읽는다. 나머지는 읽지
않는다. `mode`는 `mcp`(호스팅 MCP 서버) / `rest`(온프레미스·토큰) / `off` 중 하나다.

연동이 `none`이거나 호출이 실패해도 **문서 작성은 계속한다**. 연동은 근거를 풍부하게 할 뿐,
없다고 멈출 이유가 아니다. 대신 무엇을 못 가져왔는지 마지막 보고에 한 줄로 남긴다.

## 1. 온보딩 (`/product-spec:init`)

`references/onboarding.md`의 인터뷰 순서를 따른다. 요약하면:

1. 리포를 스캔해 언어·프레임워크·구조를 파악하고 `docsDir` 후보를 제안한다
2. 세 슬롯을 순서대로 묻는다. "안 씀"도 정상적인 답이다
3. 고른 툴의 `references/tools/<type>.md`에서 **연결 명령어와 토큰 발급 위치**를 그대로 안내한다.
   `claude mcp add` 실행과 OAuth 승인은 사용자가 직접 한다 — 대신 해주려 하지 않는다
4. `.claude/product-spec.json`을 쓴다 (`assets/product-spec.config.example.json`이 기준)
5. 연결된 툴마다 읽기 전용 호출을 한 번씩 해서 실제로 되는지 확인하고 결과를 보고한다
6. 이어서 첫 스펙 초안을 만들지 물어본다

## 2. 신규 작성 (`/product-spec:new`)

### 2-1. 코드에서 사실 수집

이 순서로 훑는다. 전부 다 읽으려 하지 말고 구조부터 잡는다.

1. `README`, `package.json`/`pyproject.toml`/`go.mod` — 제품 이름, 스크립트, 의존성
2. 진입점과 라우팅 — 어떤 화면·엔드포인트가 있는가
3. 데이터 모델 — 스키마, 마이그레이션, 타입 정의
4. API 핸들러 — 메서드·경로·요청/응답
5. `.env.example`, 설정 파일 — 외부 연동과 필수 환경변수
6. 최근 커밋 메시지 30개 — 최근 무엇에 집중했는가

### 2-2. 연동에서 맥락 수집

`tracker`가 있으면 최근 이슈에서 배경·목표를, `chat`이 있으면 관련 채널 스레드에서 결정
사유를 가져온다. 호출 방법은 각 툴 참고 문서에 있다. 여기서 얻은 것은 **`problem`,
`users`, `metrics` 섹션의 재료**다 — 코드에는 답이 없는 부분이기 때문이다.

### 2-3. 문서 작성

`assets/SPEC_TEMPLATE.md`를 그대로 뼈대로 쓴다. 섹션 정의와 필수/선택 구분은
`references/spec-format.md`에 있다. 반드시 지킬 것:

- 파일 경로: `<docsDir>/<specIdPrefix>-<번호>-<슬러그>.md` (예: `docs/specs/DM-001-payment-widget.md`)
  번호는 `docsDir`의 기존 파일 중 가장 큰 값 + 1
- frontmatter의 `last_synced_commit`에 현재 HEAD의 짧은 해시를 넣는다. 이게 다음 갱신의 기준점이다
- 코드에 답이 없는 섹션(`problem`, `users`, `metrics`)은 **비운 채 `spec:human` 블록**으로 두고,
  `> ❓ 확인 필요:` 질문을 남긴다. 지어내지 않는다
- **1부 본문에는 `경로:줄번호`를 달지 않는다.** 근거는 `sources` 섹션에 섹션 단위로 모은다
- 마지막에 `open-questions` 섹션을 문서 전체의 `❓ 확인 필요`로 다시 만든다

### 2-4. 마무리

작성이 끝나면 이렇게 보고한다.

```
✅ docs/specs/DM-001-payment-widget.md 작성 (기준 커밋 a1b2c3d)
   자동 채움: 흐름, 화면, 기능, 안 하는 것 + 개발 참고 전체
   확인 필요 3건: 왜 만드나 / 누가 쓰나 / 성공 지표 → 8번 섹션에 목록으로 모아 뒀습니다
   연동: Jira DM-142 참조함, Slack 미연결
```

`> ❓ 확인 필요` 항목은 목록으로 다시 보여주고, 지금 답해주면 바로 채워 넣겠다고 제안한다.

## 3. 갱신 (`/product-spec:update`)

**이 스킬에서 가장 중요한 동작이다.** 전체 절차는 `references/update-protocol.md`에 있고,
반드시 읽고 그대로 따른다. 요지만 옮기면:

1. frontmatter의 `last_synced_commit`을 읽는다. 없으면 신규 작성으로 처리한다
2. `git diff --name-status <last_synced_commit>..HEAD`로 변경 파일을 모은다.
   git이 없거나 실패하면 참고 문서의 폴백 경로를 쓴다 (사용자에게 범위를 묻는다)
3. 파일→섹션 매핑표로 **영향받은 섹션만** 고른다
4. 그 섹션만 다시 쓴다. `<!-- spec:human -->` ~ `<!-- /spec:human -->` 사이는 **원문 그대로
   복사한다.** 다듬거나 옮기거나 요약하지 않는다
5. `changelog`에 한 줄 추가, `spec_version`을 semver로 올리고, `last_synced_commit`과
   `last_synced_at`을 갱신한다
6. **변경이 없으면 파일을 수정하지 않는다.** "변경 없음"이라고 보고하고 끝낸다.
   의미 없는 diff를 만드는 순간 팀이 이 문서의 변경 이력을 안 믿게 된다

## 4. 드리프트 점검 (`/product-spec:check`)

문서를 고치지 않고 **차이만 보고한다.** 두 방향 모두 본다.

- 스펙에는 있는데 코드에 없다 → 지워진 기능이 문서에 남아 있다
- 코드에는 있는데 스펙에 없다 → 문서화되지 않은 기능이 늘었다

출력은 표 하나 + 한 줄 요약. 마지막에 `/product-spec:update`로 반영할지 물어본다.
CI에서 돌 때는 경고만 남기고 빌드를 깨뜨리지 않는다 (`assets/ci/` 참고).

---

## 5. 발행 (`/product-spec:publish`)

리포의 Markdown이 원본이고, 위키는 **복사본**이다. 이 방향을 뒤집지 않는다.

1. `wiki` 슬롯의 참고 문서를 읽고 해당 API로 페이지를 만들거나 갱신한다
2. 페이지 최상단에 "이 문서는 `<리포 경로>`에서 자동 생성됩니다. 여기서 수정하면 다음 갱신 때
   사라집니다." 안내를 넣는다
3. 만든 페이지 URL을 frontmatter의 `wiki_url`에 기록한다
4. `chat` 슬롯이 있으면 설정된 채널에 링크와 변경 요약을 알린다

**발행·알림은 외부에 나가는 동작이다.** 실행 전에 무엇을 어디에 올릴지 보여주고 확인을 받는다.

## 지켜야 할 선

- **사람이 쓴 블록은 손대지 않는다.** 오타가 보여도 그대로 둔다. 고칠 게 있으면 따로 알린다
- **코드에서 확인되지 않은 것은 쓰지 않는다.** 추론은 `> ❓ 확인 필요:`로 남긴다
- **한 번에 한 제품.** 모노레포면 어느 패키지인지 먼저 확정한다
- **문서 언어는 `config.language`를 따른다.** 기본값은 한국어다
- 스펙 문서 외의 파일은 수정하지 않는다. 설정 파일 생성은 온보딩 때만
