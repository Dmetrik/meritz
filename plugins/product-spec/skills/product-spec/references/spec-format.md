# 표준 Product Spec 양식

빈 뼈대는 `assets/SPEC_TEMPLATE.md`에 있다. 이 문서는 각 섹션에 **무엇을 쓰고 무엇을 쓰지
않는가**를 정의한다.

## 이 문서를 누가 읽는가

**기획자와 디자이너가 주 독자다.** 개발자도 보지만, 개발자는 아쉬우면 코드를 열어 볼 수 있고
기획자·디자이너는 그럴 수 없다. 그래서 양식이 두 부분으로 나뉜다.

| | 읽는 사람 | 담는 것 |
|---|---|---|
| **Ⅰ부 제품** (표제부 + 10개 절) | 기획·디자인·개발 모두 | 배경, 사용자, 시나리오, 화면, 기능 요구사항, 범위 제외, 성공 지표 |
| **Ⅱ부 개발 참고** (7개 절) | 개발자 | 데이터·인터페이스, 권한, 연동, 비기능 요구사항, 운영, 기술 제약 |

**Ⅰ부에는 구현 용어를 쓰지 않는다.** 엔드포인트 경로, 함수 이름, 파일 경로, 라이브러리 이름이
Ⅰ부에 나오면 잘못 쓴 것이다. 그런 건 전부 Ⅱ부로 간다.

## 파일 이름과 위치

```
<docsDir>/<specIdPrefix>-<3자리 번호>-<영문 슬러그>.md
예) docs/specs/DM-001-payment-widget.md
```

번호는 `docsDir`의 기존 파일 중 가장 큰 값 + 1. 슬러그는 소문자·하이픈만 쓴다. 파일 이름은
한 번 정하면 바꾸지 않는다 — 위키 페이지와 이슈에서 이 경로를 참조하기 때문이다.

## frontmatter

```yaml
---
spec_id: DM-001              # 파일명과 동일한 ID. 고유값
title: 결제 위젯             # 제품/기능 이름 (config.language 기준)
status: draft                # draft | review | active | deprecated
spec_version: 1.0.0          # 문서 버전 (제품 버전 아님)
author: 미지정               # 작성자. 모르면 "미지정"
reviewers: []                # 검토자. 사람이 채운다
approver: 미지정             # 승인자. 사람이 채운다
last_synced_commit: a1b2c3d  # 이 문서가 반영한 마지막 커밋 (짧은 해시)
last_synced_at: 2026-09-05   # YYYY-MM-DD
repo: acme/payment-widget    # 대상 리포. 모노레포면 패키지 경로까지
tracker_ref: DM-142          # 대표 이슈 키. 없으면 생략
wiki_url:                    # 발행 후 자동 기록. 처음엔 비워 둔다
---
```

`last_synced_commit`이 이 양식의 핵심이다. 갱신은 전적으로 이 값을 기준점으로 동작한다.

### `spec_version` 올리는 기준

| 변경 | 올림 |
|---|---|
| 기능 삭제, 대상 사용자 자체가 바뀜, 안 하기로 했던 걸 하게 됨 | major (1.2.0 → 2.0.0) |
| 기능·화면 추가 | minor (1.2.0 → 1.3.0) |
| 문구 수정, 오타, 근거 보강 | patch (1.2.0 → 1.2.1) |

## 섹션 마커

부분 갱신을 가능하게 하는 장치다. **마커를 지우거나 형태를 바꾸면 갱신이 동작하지 않는다.**

```markdown
<!-- spec:section id=features -->
## 6. 기능 요구사항

(코드에서 추출한 내용. 갱신할 때마다 이 영역은 통째로 다시 쓰인다)

<!-- spec:human -->
> 결제 실패 재시도 3회는 PG사 정책상 상한이라 못 늘림. — 2026-08 PO팀
<!-- /spec:human -->
<!-- /spec:section -->
```

- `spec:section` — 갱신 단위. `id`는 아래 정의된 값만 쓴다
- `spec:human` — **사람 영역.** 갱신 시 바이트 단위로 그대로 옮긴다. 섹션 어디에나 여러 개
  둘 수 있다. 다듬기·요약·위치 이동 모두 금지
- `> ❓ 확인 필요: <질문>` — 코드로 확답할 수 없어 사람 답이 필요한 지점

## Ⅰ부 — 제품 (표제부 + 10개 절)

| id | 절 | 채우는 주체 | 내용 |
|---|---|---|---|
| `doc-info` | 표제부 | 자동+사람 | 문서 번호·버전·상태·최종 갱신·작성·검토·승인·대상 저장소. 작성/검토/승인은 사람이 채운다 |
| `summary` | 1. 개요 | 자동+사람 | 누구의 어떤 불편을 어떻게 더는지 세 문장 이내 |
| `problem` | 2. 배경 및 문제 정의 | **사람** | 코드에 답이 없다. `spec:human`으로 비워 두고 질문을 남긴다 |
| `users` | 3. 사용자 정의 | 자동+사람 | 구분·어떤 사람·사용 상황 표. 코드에서 역할 구분이 보이면 그것만 사실로 적고 나머지는 질문 |
| `flows` | 4. 사용자 시나리오 | 자동+사람 | **디자이너가 제일 먼저 보는 곳.** 대표 시나리오 1~3개를 `4.1`, `4.2`로 번호를 매겨 쓰고, 각각에 **예외 처리**를 붙인다 |
| `screens` | 5. 화면 정의 | 자동+사람 | 화면·용도·접근 권한·주요 동작 표. `5.1`에 빈 상태와 오류 상태를 반드시 적는다 |
| `features` | 6. 기능 요구사항 | 자동 | **`FR-01`부터 ID를 부여한다.** 기능·설명·사용자·우선순위(필수/권장/선택). 구현 방식이 아니라 사용자가 얻는 결과로 쓴다 |
| `scope` | 7. 범위 제외 | 자동+사람 | 제외 항목·사유·향후 검토. 여기가 비면 반드시 분쟁이 난다 |
| `metrics` | 8. 성공 지표 | **사람** | 지표·현재·목표·측정 방법 표. 코드에 답이 없다 |
| `open-questions` | 9. 미결 사항 | 자동 | `Q-01`부터 ID를 부여. 관련 절·확인 내용·담당·기한. **갱신마다 다시 만든다** |
| `changelog` | 10. 개정 이력 | 자동 | 최신이 위. 코드가 아니라 사용자에게 무엇이 달라졌는지 |

### `flows`를 잘 쓰는 법 (4절)

라우팅과 핸들러를 따라가면 흐름은 재구성할 수 있다. 다만 **코드 순서가 아니라 사용자 순서로**
쓴다.

```markdown
### 4.1 음료 주문

1. 오늘의 메뉴에서 마실 것을 고른다. 품절된 메뉴는 목록에 나오지 않는다
2. 사이즈를 고르고 요청사항을 100자까지 적을 수 있다
3. 주문하면 "준비중"으로 접수되고, 바리스타 채널에 주문 번호가 올라간다

**예외 처리** — 사이즈를 안 고르거나 요청사항이 100자를 넘으면 접수되지 않는다.
로그인 정보가 없으면 주문 자체가 실패한다.
```

절 제목은 격식 있게, 문장은 쉬운 말로. 이 둘은 충돌하지 않는다.

### `open-questions`(9절)는 자동으로 만든다

문서 안의 모든 `❓ 확인 필요`를 훑어 체크리스트 표로 모은다. 원래 자리의 `❓`는 그대로 두고,
이 섹션은 **색인** 역할만 한다. 갱신할 때마다 전체를 다시 만든다.

```markdown
| | 항목 | 관련 절 | 확인 내용 | 담당 | 기한 |
|---|---|---|---|---|---|
| ☐ | Q-01 | 2. 배경 및 문제 정의 | 어떤 불편에서 출발했나 | | |
| ☐ | Q-02 | 8. 성공 지표 | 어떤 수치가 얼마나 달라져야 하나 | | |
```

`Q-01`부터 순서대로 매긴다. 갱신 때 해소된 항목은 빠지고 번호는 다시 매긴다.

기획자가 문서를 열었을 때 **자기가 할 일이 한눈에 보이는 곳**이다. 여기가 이 문서의 실질적인
작업 목록이다.

## Ⅱ부 — 개발 참고 (7개 절)

`config.sections.optional`에서 켜고 끈다. 기본은 전부 켜져 있고, 근거가 없으면 섹션째 생략한다.
**여기서는 구현 용어와 `경로:줄번호` 인용을 자유롭게 쓴다.**

| id | 절 | 내용 |
|---|---|---|
| `data-api` | 11. 데이터 및 인터페이스 | `11.1` 데이터 구조 + `11.2` 인터페이스(메서드·경로·용도·인증·정의 위치) |
| `permissions` | 12. 권한 및 보안 | 역할별 허용 범위, 인증 방식, 민감정보 취급. **토큰·키 값은 절대 옮겨 적지 않는다** |
| `dependencies` | 13. 연동 및 의존성 | `13.1` 외부 서비스(장애 시 동작 포함), `13.2` 환경변수 **변수명만**, `13.3` 주요 라이브러리 |
| `nfr` | 14. 비기능 요구사항 | 지원 환경·접근성·성능·국제화·오류 처리·테스트. **코드에서 확인되는 것만 적고, 없으면 "확인되지 않음"으로 남긴다** |
| `ops` | 15. 배포 및 운영 | 배포 방식·실행 환경·롤백 절차·모니터링 |
| `tech-notes` | 16. 기술 제약 및 알려진 이슈 | `TN-01`부터 ID 부여. **사용자에게 영향이 가는 것은 여기 두지 말고 Ⅰ부에 사용자 관점으로 적는다** |
| `sources` | 부록. 근거 | 절별로 어떤 파일을 봤는지. 본문 서술의 출처를 확인하는 곳 |

## 문장 규칙

### Ⅰ부 — 사용자의 말로

- **구현 용어 금지.** 함수·파일·엔드포인트·라이브러리 이름이 Ⅰ부에 나오면 잘못 쓴 것이다
- **`경로:줄번호` 인용을 본문에 달지 않는다.** 근거는 부록에 절 단위로 모은다.
  읽는 흐름을 끊지 않으면서도 출처를 확인할 수 있다
- 확인된 사실은 단정형으로. "품절된 메뉴는 목록에 나오지 않는다"
- 추론은 쓰지 않는다. `> ❓ 확인 필요:`로 남긴다
- 한 항목이 두 줄을 넘으면 쪼갠다

### Ⅱ부 — 정확하게

- `경로:줄번호`까지 적는다. `src/api/payments.ts:42`
- 표를 쓸 수 있으면 표를 쓴다
- 환경변수는 이름만. 값은 절대 넣지 않는다

## 기술 사실을 사람 말로 옮기기

코드에서 발견한 것을 Ⅰ부에 적을 때는 **사용자가 겪는 일**로 바꾼다. 그대로 옮기면 기획자가
읽을 수 없고, 버리면 중요한 제약이 사라진다. 번역해서 양쪽에 적는다.

| 코드에서 본 것 | Ⅰ부에 적는 말 | Ⅱ부에도 남길 것 |
|---|---|---|
| `notifySlack`이 `async`인데 `await`가 없다 | "알림 전송이 실패해도 화면에는 정상으로 보인다" (4절 예외 처리) | 원문 그대로 + 근거 |
| 취소 엔드포인트가 없다 | "주문을 되돌릴 수 없다. 바리스타에게 직접 말해야 한다" (7. 범위 제외) | — |
| `SELECT *`로 전체 컬럼 반환 | (사용자 영향 없음 — Ⅰ부에 적지 않는다) | 원문 그대로 |
| `role === "staff"` 검사 | "바리스타만 들어올 수 있다" (5. 화면 정의의 접근 권한) | 역할 표 + 근거 |
| DB에 상태 제약이 없다 | (사용자 영향 없음 — Ⅰ부에 적지 않는다) | 원문 그대로 |

판단 기준은 하나다. **사용자가 그 일을 겪는가?** 겪으면 Ⅰ부에 사용자 관점으로, 안 겪으면 Ⅱ부에만.
