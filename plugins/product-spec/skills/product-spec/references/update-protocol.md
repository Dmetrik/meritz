# 갱신 프로토콜

문서를 다시 쓰는 게 아니라 **바뀐 부분만 고친다.** 전체를 다시 생성하면 사람이 쓴 문장이
사라지고, 매번 diff가 수백 줄이 되어 아무도 변경 이력을 읽지 않게 된다.

## 1단계: 기준점 찾기

frontmatter의 `last_synced_commit`을 읽는다.

| 상황 | 처리 |
|---|---|
| 값이 있고 유효한 커밋 | 그 커밋부터 HEAD까지가 갱신 범위 |
| 값이 없거나 비어 있음 | 신규 작성으로 처리한다 (`SKILL.md` §2) |
| 값은 있는데 리포에 없는 커밋 (rebase·force push) | 사용자에게 알리고 범위를 묻는다. 임의로 전체 재작성하지 않는다 |

## 2단계: 변경 파일 수집

```bash
git diff --name-status <last_synced_commit>..HEAD
git log --oneline <last_synced_commit>..HEAD
```

`--name-status`의 `A`(추가) `M`(수정) `D`(삭제)를 구분해서 기억한다. 삭제된 파일은
**문서에서 해당 항목을 지우는** 근거이므로 특히 놓치면 안 된다.

### 이슈 키를 뽑을 때 걸러야 할 것

커밋 메시지에서 이슈 키를 정규식으로 긁으면 **엉뚱한 것이 딸려 온다.** 실제로 겪는 두 가지:

1. **스펙 ID 자신** — `specIdPrefix`가 트래커 프로젝트 키와 같으면 (`CO-001` 같은) 문서 ID가
   이슈 키로 잡힌다. `spec_id` 값은 반드시 제외한다
2. **문서 커밋** — `docs(spec): …` 처럼 스펙 문서만 고친 커밋의 메시지는 이번 변경의 근거가
   아니다. **코드 파일을 건드린 커밋**의 메시지에서만 뽑는다

```bash
# 코드를 건드린 커밋만 골라 이슈 키를 뽑고, 스펙 ID 는 제외한다
git log --pretty=%H <base>..HEAD -- . ":(exclude)docs/" |
  xargs -I{} git log -1 --pretty='%s%n%b' {} |
  grep -oE '[A-Z][A-Z0-9]+-[0-9]+' | sort -u | grep -v '^CO-001$'
```

트래커 연동이 있으면 뽑은 키가 실제로 존재하는 이슈인지 조회해 한 번 더 거른다.
존재하지 않으면 변경 이력에 적지 않는다.

### git을 쓸 수 없을 때

git이 설치돼 있지 않거나 실행이 실패하는 환경이 있다 (예: macOS에서 Xcode Command Line
Tools가 깨진 경우 `xcrun: invalid active developer path` 오류). 이때는:

1. 사용자에게 상황을 알린다. 조용히 다른 방식으로 넘어가지 않는다
2. `last_synced_at` 이후 수정된 파일을 찾아 후보로 삼는다
   ```bash
   find . -newermt "2026-09-05" -type f -not -path "*/node_modules/*" -not -path "*/.git/*"
   ```
3. 후보 목록을 보여주고 갱신 범위를 확인받은 뒤 진행한다
4. 삭제된 파일은 이 방식으로 알 수 없다. 문서에 있는 항목이 실제 코드에 있는지 역방향으로
   확인해 보완한다 (드리프트 점검과 동일한 절차)

## 3단계: 파일 → 섹션 매핑

변경 파일 경로로 다시 쓸 섹션을 고른다. 여러 섹션에 걸리면 전부 포함한다.

| 변경 파일 패턴 | 다시 쓸 섹션 |
|---|---|
| `**/routes/**`, `**/pages/**`, `**/app/**/page.*`, `**/screens/**` | `screens`, `flows` |
| `**/api/**`, `**/handlers/**`, `**/controllers/**`, `**/*.route.*`, OpenAPI 스펙 | `data-api`, `features`, `flows` |
| `**/models/**`, `**/entities/**`, `**/schema*`, `**/migrations/**`, `*.prisma`, `*.sql` | `data-api` |
| `package.json`, `pyproject.toml`, `go.mod`, `Gemfile`, `*.lock` | `dependencies` |
| `.env.example`, `**/config/**`, `*.config.*` | `dependencies`, `ops` |
| `**/middleware/**`, `**/auth/**`, `**/guards/**`, `**/policies/**` | `permissions` |
| `Dockerfile`, `docker-compose*`, `.github/workflows/**`, `**/deploy/**`, `k8s/**` | `ops` |
| `README*`, `docs/**`(스펙 제외) | `summary`, `scope` |
| 위 어디에도 안 걸리는 소스 파일 | `features` |
| 테스트 파일·설정 추가·삭제 | `nfr` (테스트 항목). 그 외 절은 다시 쓰지 않는다 |

`problem`, `users`, `metrics`는 **어떤 코드 변경으로도 다시 쓰지 않는다.** 사람의 영역이다.

### 부정 서술을 담은 섹션은 별도로 확인한다

위 표는 "이 파일이 바뀌면 이 섹션의 내용이 바뀐다"만 다룬다. 그런데 `scope`의 **하지 않는 것**,
`tech-notes`의 "…없음" 항목, `permissions`의 역할 표는 **없다는 주장**을 담고 있어서, 기능이 하나
추가되면 표에 걸리지 않아도 거짓이 된다.

그래서 엔드포인트·화면·엔티티가 **추가되거나 삭제되면** 위 매핑과 별개로 이 세 섹션을 반드시
다시 읽고, 새 코드가 반증하는 문장이 있으면 고친다.

| 코드 변화 | 추가로 확인할 섹션 | 왜 |
|---|---|---|
| 엔드포인트·화면 추가 | `scope`, `permissions`, `tech-notes` | "범위 제외"에 적혀 있던 게 이제 된다 |
| 엔드포인트·화면 삭제 | `scope`, `features`, `flows`, `screens` | 문서에만 남은 기능이 된다 |
| 권한 검사 추가·변경 | `permissions`, `screens`, `tech-notes` | 역할 표·화면 접근 권한·알려진 이슈가 함께 움직인다 |
| 상태값·열거형 확장 | `data-api`, `tech-notes` | 새 값이 기존 분기에 안 들어가 있으면 그 자체가 이슈다 |
| 접근성·브라우저 지원 관련 변경 | `nfr`, `screens` | 지원 범위가 바뀌면 화면 정의도 같이 움직인다 |

## 4단계: 섹션 재작성

고른 섹션마다:

1. `<!-- spec:section id=... -->` ~ `<!-- /spec:section -->` 사이를 찾는다
2. 그 안의 모든 `<!-- spec:human -->` ~ `<!-- /spec:human -->` 블록을 **원문 그대로 떼어
   보관한다.** 공백·줄바꿈·오타까지 바이트 단위로 보존한다
3. 자동 영역을 새로 쓴다. 변경된 파일만이 아니라 **해당 섹션의 현재 코드 전체를 다시 본다**
   — 변경 파일만 보면 기존 내용과 앞뒤가 안 맞는다
4. 보관해 둔 human 블록을 **원래 있던 위치에** 되돌린다
5. 미해결 `> ❓ 확인 필요:` 항목도 그대로 유지한다. 이번 변경으로 답이 생겼으면 채운다
6. **문서 전체의 근거 줄번호를 다시 대조한다.** 코드를 몇 줄 끼워 넣으면 그 아래의 모든 줄이
   밀린다. 이번에 다시 쓰지 않은 섹션의 인용도 같이 틀어지므로, 같은 파일을 인용한 곳은
   **섹션과 무관하게 전부** 확인한다. 이 단계를 빼먹으면 문서는 멀쩡해 보이는데 근거 링크만
   조용히 어긋난다 — 가장 알아채기 어려운 실패다
7. **ID는 절대 바꾸지 않는다.** `FR-`·`TN-` 번호는 티켓·QA가 참조한다. 기능이 없어지면
   번호를 재사용하지 말고 행을 지우거나 "삭제됨"으로 표시한다. 새 기능은 다음 번호를 받는다
8. **Ⅰ부를 다시 쓸 때는 사람 말로 쓴다.** 코드에서 새로 발견한 기술적 사실을 1부에 그대로
   옮기지 않는다. `spec-format.md`의 "기술 사실을 사람 말로 옮기기" 표를 따라 번역하고,
   원문은 Ⅱ부(`tech-notes` 등)에 남긴다. Ⅰ부에는 `경로:줄번호`를 달지 않는다
9. **`open-questions`를 다시 만든다.** `Q-` 번호는 매번 새로 매긴다 (해소된 항목이 빠지므로). 문서 전체의 `❓ 확인 필요`를 훑어 체크리스트를
   새로 생성한다. 이번 변경으로 답이 생긴 항목은 목록에서 빠져야 한다

### 사람 블록에 대한 절대 규칙

- 내용을 다듬지 않는다. 오타가 있어도 그대로 둔다
- 위치를 옮기지 않는다
- 여러 개를 하나로 합치지 않는다
- 내용이 코드와 모순돼도 지우지 않는다. 대신 갱신 보고에 "사람이 쓴 내용과 코드가 다릅니다"로
  알리고 판단은 사람에게 맡긴다

## 5단계: 이력과 버전

`changelog` 섹션 맨 위에 한 줄 추가한다.

```markdown
| 2026-09-05 | 1.3.0 | a1b2c3d..f4e5d6c | 정기 결제 해지 API 추가, 재시도 상한 3→5회 | DM-201, DM-207 |
```

- 이슈 키는 `git log` 메시지에서 뽑고, 트래커 연동이 있으면 제목까지 확인해 요약에 반영한다
- 요약은 **코드가 아니라 사용자에게 무엇이 달라졌는가**로 쓴다.
  "PaymentService 리팩터링"(X) → "정기 결제를 앱에서 직접 해지할 수 있음"(O)

frontmatter를 갱신한다.

```yaml
spec_version: 1.3.0          # spec-format.md의 semver 기준으로 올림
last_synced_commit: f4e5d6c  # 현재 HEAD 짧은 해시
last_synced_at: 2026-09-05
```

## 6단계: 보고

```
✅ docs/specs/DM-001-payment-widget.md 갱신 (a1b2c3d..f4e5d6c, 커밋 12개)
   다시 쓴 섹션: data-api, features, dependencies
   보존한 사람 영역: 3개 블록 (변경 없음)
   문서 버전: 1.2.1 → 1.3.0
   ⚠️ 사람이 쓴 "재시도 3회 상한" 메모가 현재 코드(5회)와 다릅니다. 확인해 주세요.
```

### 변경이 없을 때

```
변경 없음. docs/specs/DM-001-payment-widget.md는 최신 상태입니다 (기준 f4e5d6c).
```

**파일을 저장하지 않는다.** `last_synced_at`만 바꾸는 것도 하지 않는다. 의미 없는 커밋이
쌓이면 팀이 이 문서의 변경 이력을 신뢰하지 않게 된다.

## 드리프트 점검

`/product-spec:check`는 문서를 **고치지 않고** 차이만 본다. 양방향으로 확인한다.

### 문서 → 코드 (사라진 것)

문서에 적힌 엔드포인트·화면·엔티티·환경변수를 코드에서 찾는다. 없으면 드리프트.

### 코드 → 문서 (누락된 것)

라우트·API 핸들러·스키마·환경변수를 코드에서 모아 문서와 대조한다. 문서에 없으면 드리프트.

### 출력

```markdown
## 드리프트 점검 결과 — DM-001-payment-widget

기준 커밋: a1b2c3d (2026-08-12) → 현재 HEAD: f4e5d6c, 그동안 커밋 12개

| 방향 | 항목 | 위치 | 판단 |
|---|---|---|---|
| 코드에만 있음 | `DELETE /api/subscriptions/:id` | `src/api/subscriptions.ts:88` | 문서 누락 |
| 코드에만 있음 | `SLACK_WEBHOOK_URL` | `.env.example:12` | 문서 누락 |
| 문서에만 있음 | `POST /api/payments/legacy` | — | 제거된 듯 |

요약: 누락 2건, 잔존 1건. `/product-spec:update`로 반영할 수 있습니다.
```

차이가 없으면 한 줄로 끝낸다: `드리프트 없음. 문서와 코드가 일치합니다 (기준 f4e5d6c).`

### CI에서 돌 때

`assets/ci/`의 예시 워크플로는 **경고만 남기고 빌드를 실패시키지 않는다.** 도입 초기에 CI를
빨갛게 만들면 팀은 문서를 고치는 대신 검사를 꺼버린다. 실패로 바꾸는 건 팀이 이 흐름에
익숙해진 뒤에 결정할 일이다.
